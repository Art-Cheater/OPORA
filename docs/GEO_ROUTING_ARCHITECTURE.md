# Маршруты

Routing postponed. Recommended architecture researched separately.
В текущем этапе Valhalla, OSRM, GraphHopper, VROOM и OR-Tools не
разворачиваются. Обычный `scripts/deploy.sh` от них не зависит.
Кнопки «Построить маршрут» в интерфейсе нет: план мастера показывает
точки выбранных работ и работы рядом, без линии маршрута.
`flask geo-status` пишет `Disabled / not in current scope`.
Код `RoutingService` и `docker-compose.routing.yml` оставлены как задел
и ничего не запускают сами.

Фронтенд не знает, какой движок считает дорогу. Когда маршруты вернут
в задачу, сервер вызывает `RoutingService`, карта рисует линию только если
пришла дорожная геометрия. Прямая между точками не подставляется.

`POST /api/routes` принимает точки `{lat, lon, id}`, режим `driving` и флаг
`optimize`. Ответ: `geometry`, `distance_m`, `duration_s`, `ordered_stops`,
`legs`. `optimize: true` сейчас отвечает `409 optimization_not_configured`:
порядок точек не переставляется молча.

Рабочий план использует `POST /work-orders/route.json`. Точка без координат
в линию не входит и перечисляется отдельно. Сомнительное качество
(`STREET`, `SETTLEMENT`, `INTERPOLATED`, `UNKNOWN`) показывается предупреждением.

## Что нужно ОПОРЕ

Один мастер, один автомобиль, один план. Обычно это единицы и первые десятки
точек, верхняя проверка API — 50. Нужны километраж, время и линия на карте.
Пошаговая навигация, пробки и отдельный график спецтехники не требуются.
Пеший профиль можно оставить в движке, основной режим — автомобиль.

Оптимизация порядка для одной бригады — это задача коммивояжёра, не обычный
маршрут A→B→C. Пока мастер задаёт порядок сам. Перестановка понадобится,
когда появится отдельное требование «разложить план оптимально». Несколько
бригад и окна времени — уже VROOM или OR-Tools, не первый шаг.

## Сравнение

| | Valhalla | OSRM | GraphHopper |
| --- | --- | --- | --- |
| Уже в проекте | да, `docker-compose.routing.yml` | совместимый URL в `RoutingService` | нет |
| Авто и пешком | да | да, разными профилями | да |
| Матрица | да | да, отдельный сервис | да |
| Snap к дороге | `locate` | nearest | snap |
| Один экипаж, лучший порядок | `optimized_route` | Trip | нет из коробки |
| Несколько бригад | нет | нет | нет |
| Лицензия | MIT | BSD | Apache 2.0 |
| Сложность | свой PBF и tiles | свой PBF и extract | свой PBF и graph |

Рекомендация: **Valhalla**. Код, compose-файл и документация
`docs/VALHALLA_SETUP.md` уже есть. OSRM короче в простом A→B, но второй
стек ничего не даёт, пока Valhalla не отклонена. GraphHopper не подключён.
Внешний API маршрутов не нужен, если есть место на сервере под область.

VROOM и OR-Tools не ставить, пока нет нескольких бригад или окон по времени.

PostGIS сейчас не нужен. Ближайшие работы считаются по `latitude`/`longitude`
и haversine, выборка карты ограничена bbox и 500 точками. Расширение имеет
смысл позже, если точек станет десятки тысяч или появятся полигоны зданий
в запросах. Отдельный контейнер PostGIS не добавлять заранее.

## Ресурсы

Текущий compose: PostgreSQL 17, web (Gunicorn), nginx, синхронизация ЕИС,
опрос заявок с лимитом 768 МБ. Отдельного геосервиса нет. Конкретный объём
RAM production-сервера в репозитории не указан: перед включением Valhalla
нужно проверить свободную память на машине.

| Вариант | CPU | RAM | Диск | Что принести |
| --- | --- | --- | --- | --- |
| A. Внешний API | без своего графа | без своего графа | без своего графа | договор и ключ провайдера |
| B. Только Кировская область | 2–4 ядра на сборку графа | 2–4 ГБ для Valhalla | PBF области: десятки–первые сотни МБ; tiles 1–3 ГБ | файл PBF и решение включить compose |
| C. Больше области, например ПФО | 4–8 ядер | 8–16 ГБ | tiles порядка 10–30 ГБ | больший PBF и отдельный запас диска |

Вариант B достаточный. Обновлять граф вместе с OSM, ориентир раз в квартал:
положить новый PBF в `data/valhalla` и пересобрать tiles. Каталог не в git.

Включение, когда PBF уже лежит на сервере:

```text
ROUTING_PROVIDER=valhalla
ROUTING_BASE_URL=http://valhalla:8002
```

```text
docker compose -f docker-compose.yml -f docker-compose.routing.yml up -d
```

`scripts/deploy.sh` этот override сам не поднимает и не скачивает PBF.
Пока маршруты отложены, эти строки не задают и контейнер не запускают.

Свой Photon для геокодера области — ещё около 1–2 ГБ RAM и выгрузка OSM
той же области. Это отдельное решение, публичный Nominatim остаётся рабочим
вариантом для редких подсказок.
